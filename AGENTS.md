# Rules for Agents

Incidents and long-form background for these rules: `docs/src/agent-incidents.md`.

- **GOLDEN RULE -- never compile, always download a prebuilt binary**: Source every package as a prebuilt: a Homebrew cask/formula (`nix/darwin/default.nix`), a mise binary backend (`aqua:`/`npm:`/`pipx:` in `nix/home/default.nix`), or a nix derivation that *fetches* the upstream release binary. Verify with `nix build .#darwinConfigurations.ranolp-work-MBP-26.system --dry-run`: if any real package (not a home-manager wrapper/activation/stub derivation) appears under "will be built", it is compiling -- stop and re-source it. Worked example in the doc: `nix/home/darwin/default.nix` fetches the official espanso release and `ditto`s the notarized app into `~/Applications` at activation.
- **ALWAYS BE DECLARATIVE -- a package changes in its declaration file, never on the machine**: Answer "upgrade X" by editing the declaration and handing over the rebuild. A CLI version lives in the `[tools]` table of `nix/home/mise-global.toml` (npm-backed as `"npm:<pkg>" = "<version>"`, pipx-backed as `"pipx:<pkg>" = "<version>"`); a GUI app or formula lives in `homebrew.casks` / `homebrew.brews` in `nix/darwin/default.nix` (names only -- a cask upgrade is a `brew upgrade` the rebuild performs, not a version edit); everything nixpkgs ships moves with `nix flake update` against `nix/flake.lock`. Report "what is upgradeable?" from those same three surfaces -- `mise outdated`, `brew outdated --greedy`, and the `lastModified` of each `nix flake metadata` input -- and name the file whose line would change. `declarative-package-guard.py` denies the imperative form (`npm i -g`, `pipx install`, `cargo install`, `brew install|upgrade`, `mise use -g`, `nix profile install`) and names the file to edit instead.
- **Build it green BEFORE handing the rebuild over**: `--dry-run` prints the plan and stops, so it is blind to a fixed-output hash mismatch, an eval error, or a failing builder. Run BOTH -- the dry-run for the "will be built" audit, then the real build `cd ~/.dotfiles/nix && nix build .#darwinConfigurations.ranolp-work-MBP-26.system --no-link` (no sudo needed) -- and hand over the rebuild command only after the full build exits 0. Pin a hand-added AMO addon to an immutable `/downloads/file/<id>/<name>-<ver>.xpi` URL rather than the moving `latest.xpi` alias; a clean dry-run once hid exactly that break (doc).
- **The user runs the rebuild, not you**: After modifying any file under `nix/home/configs/`, finish the edits, then hand the user the apply command for THIS host to run in their own shell -- macOS: `! sudo darwin-rebuild switch --flake ~/.dotfiles/nix#ranolp-work-MBP-26`; Linux/WSL: `! home-manager switch --flake ~/.dotfiles/nix#ranolp-archwsl -b before-hm`. Say plainly that the change is pending until they run it. Hand it over ONCE per generation, in the message where the batch of edits finishes, at the END of the message that answers what the user actually asked. The `rebuild-enforcer` Stop hook shows the same reminder, also once per generation.
- **Direct main git workflow allowed here**: When requested, agents should create commits on `main` and push `main` to `origin` in this repository. Inspect status/diff first, stage explicit paths, and keep PR workflows out of scope.
- **REUSE 3.3 compliance -- every new file carries an annotation**: After adding a file, append its path to the matching `[[annotations]]` block in `REUSE.toml` (`precedence = "aggregate"`, `SPDX-FileCopyrightText = "2026 RanolP"`, `SPDX-License-Identifier = "MIT"`), extending an existing block that already covers that area. A vendored third-party file keeps its upstream copyright and license instead, with a comment naming the exact upstream version (see the `adf-schema-56.7.3.json` block). Verify with `reuse lint 2>&1 | grep <your-new-path>`, which must print nothing. Whole-project `reuse lint` exits non-zero today -- 123 legacy files predate the convention and stay untouched, so a red overall run says nothing about your change.
- **Never edit global config directly**: All Claude config lives in `nix/home/configs/claude/` in this repo -- edit there, never `~/.claude/settings.json` or any other file under `~/.claude/`.
- **A hook is verified in a container BEFORE it is deployed**: A `PreToolUse` hook on the `Bash` matcher fronts every Bash call in every session, so a bad one is a total work stoppage that only a rebuild can lift. Run `./scripts/verify-claude-hook.sh nix/home/configs/claude/hooks/<name>.py` first; a hook that scores any `STOP` never gets registered (exit-code contract and test battery in the doc). Only after it is clean: (1) add its `".claude/hooks/<name>.py" = { source = ./configs/claude/hooks/<name>.py; executable = true; }` entry to `nix/home/default.nix` -- one explicit entry per script, never directory recursion; (2) `git add` the script, because a flake reads the git tree and an unstaged file is invisible to the rebuild; (3) hand the user the rebuild and wait; (4) confirm `ls -l ~/.claude/hooks/<name>.py` resolves into `/nix/store/...`; (5) register it in `nix/home/configs/claude/settings.json`. The same one-entry-per-item rule governs skills: a new `nix/home/configs/.agents/skills/<name>/` needs its own `<name> = localSkill "<name>";` line in the `skills` attrset.
